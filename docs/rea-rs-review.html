How closely rea-rs tracks morluto/rea

It tracks the pitch, not the product. rea-rs is a clean-room Rust sketch of “one local MCP that inspects native binaries.” morluto/rea is a Node toolkit with on the order of 150 MCP tools, external decompilers, and an evidence session around every result.

Compared against morluto/rea main on 12 Oct 2026, and rea-rs 95171c9. Tool names were read from src/contracts, not from a live tools/list.

Fidelity

API compatibility is none: different tool names, no Evidence records, no provider session, protocol pinned to 2024-11-05 with text-only results. The shared idea is a stdio MCP plus a JSON CLI for static native inspection. Everything past that — decompilation, call graphs, JavaScript, web, Android, .NET, Frida, firmware, WASM — is absent. LE / DOS/4GW support is original work in this tree, not a port.

What this tree does on its own

  • Uniform Target for Mach-O, ELF, PE, and LE, with virtual-address to file-offset translation. Fat Mach-O picks a host slice.
  • LE is checked before goblin, because goblin peeks those files as PE.
  • Function discovery and string cross-references were added to read WAR.EXE. They live on the CLI. The Warcraft notes in docs/warcraft-1-demo-re.md still say fixups are not applied; load_le now calls apply_fixups and ignores the result.
  • The module comment at the top of le.rs still says fixups are out of scope. That comment is false.

Review of the LE fixup loader

Commit 2e7687b teaches LeImage::apply_fixups to rewrite internal relocations, and load_le runs it on every LE binary. A single internal 32-bit fixup on an identity page map (the Warcraft demo) can land correctly. The walker does not follow the fixup-record layout it cites, and a slipped cursor writes later records into the image as if they were fixups. No test builds a real fixup record: synthetic() leaves the fixup tables at 0, so apply_fixups returns Ok(0).

bug

Source lists are parsed before the ordinal and target

crates/rea-core/src/le.rs:288

The source-list flag replaces the single i16 offset with a count. The count offsets come after the ordinal and the target, not before them. This code reads the offsets immediately, so the ordinal and target are taken from the list and the rest of that page shifts. A short list only breaks the inner loop, then still parses an ordinal from whatever follows.

Read the count, parse the ordinal and target tail, then read the offsets. On a short read, stop the page. A fixture with one list record followed by a normal type-7 record would have caught this.

bug

Skipped records do not consume their tail

crates/rea-core/src/le.rs:324

Imports, a bad object number, and 16-bit selector fixups continue without finishing the record. The next iteration treats the middle of that record as a new fixup and can patch the image. Selector internals have no target-offset field, but the parser always reads one before rejecting them. Reads are not clamped to the page’s fixup range, so a long record steals the next page’s bytes. load_le drops the Result (loader.rs:40), and apply_fixups never returns Err.

Decode a record to its end before deciding to apply it. If a read would pass the page, abandon the rest of that page. Surface a real parse failure from load_le.

bug

Page bases are keyed by file page, then indexed by logical page

crates/rea-core/src/le.rs:240

page_vaddr is filled with the file page number from the object page table. Fixups are applied with the logical page index. Those match only for an identity map, which WAR.EXE has and scattered maps do not. An oversized mapsize indexes off self.pages.pages and panics inside load. Address 0 is also used as the “unset” sentinel. A 32-bit store that crosses a page writes four file-contiguous bytes; adjacent virtual pages are not adjacent in the file unless the map is identity.

Build one virtual address per logical page, the same way translate uses pagemap. Bounds-check and return Err. Split stores that cross a page.

bug

16-bit offset fixups store a truncated linear address

crates/rea-core/src/le.rs:395

Source type 5 stores the object-relative offset, and only when it fits in a u16. This writes the low 16 bits of object.base + offset. That matches the object offset only when the base is 64K-aligned and the offset is below 64K, which is why WAR.EXE hides it.

For source type 5, write target_offset + additive and skip the site when the sum does not fit in u16. Keep the linear address for source type 7.

suggestion

The header comment and the tests still describe the old scope

crates/rea-core/src/le.rs:7

The module comment says fixups are not handled. synthetic() never sets the fixup tables, so the bugs above are invisible. Source type 8 (32-bit self-relative) is skipped even though the stored dword is target - (src + 4). The additive flag means “add to the bytes already at the source”; this always overwrites. Non-additive type-7 records, which Watcom usually emits, are unaffected.

Update the comment. Extend synthetic() with one internal type-7 record, one source-list record, and one non-identity page.

nit

The stats example clones an unused buffer and can panic

crates/rea-core/examples/le_fixup_stats.rs:8

bytes is cloned and then unused. The sample read panics when translate returns an offset in the last three bytes. The hardcoded address 0x109eb only means anything for one binary.

Move bytes into patched, and print the sample only when off + 4 <= patched.len().
